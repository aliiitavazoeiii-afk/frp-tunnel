# Trust + Mieru Dual Tunnel — v1.1.0 current context

This file supersedes conflicting operational details in older handoff notes. Older context remains useful for incident history.

## Current operator interface

Canonical operator scripts:

- `dual-install-foreign.sh` — the only normal foreign installer entry point
- `dual-install-iran.sh` — the only normal Iran installer/upgrade entry point
- `dual status` — interactive production management menu
- `dual health --full` — non-interactive full health

See `SIMPLE-INSTALL.md`.

## Architecture that must remain unchanged unless deliberately benchmarked

```text
x-ui public VLESS/REALITY :443
  -> dispatcher :7990
     -> Trust path :7991
        TCP -> Trust carrier :7993
        UDP -> Trust XUDP
     -> Mieru path :7992
        TCP -> Mieru carrier :7994
        UDP -> Mieru XUDP
```

Mieru production settings remain:

```text
MULTIPLEXING_OFF
HANDSHAKE_STANDARD
```

This is intentionally preserved because the current production combination no longer shows the earlier video-freeze problem reported by the operator. Do not casually re-enable Mieru multiplexing.

## v1.1 health changes

The old aggressive background health profile is retired.

Dispatcher health profile applied by the v1.1 manager:

```text
interval: 120
lazy: true
max-failed-times: 2
```

Autoheal timer:

```text
OnUnitActiveSec=5min
RandomizedDelaySec=90s
```

Autoheal direct health can restart only the failed role carrier. HTTP on `7991`/`7992` is no longer treated as proof of XUDP health because TCP on those ports is intentionally routed directly to the carrier. Real SOCKS UDP-associate probes are used for XUDP diagnosis.

A single role UDP/XUDP failure is reported but must not restart the shared bridge. Shared `dual-xudp-bridge` restart is allowed only after both Trust and Mieru UDP/XUDP paths repeatedly fail while both direct carriers are healthy.

## v1.1 health screen

`dual health --full` checks separately:

- services
- direct Trust/Mieru carrier HTTP
- forced Trust/Mieru TCP path HTTP
- repeated Telegram connectivity per role
- real UDP/XUDP per role
- dual dispatcher HTTP / Telegram / UDP

This was added because one successful generic HTTP 204 is insufficient to explain application-specific failures and does not validate UDP/XUDP.

## Foreign replacement invariant

The normal replacement flow is now through `dual status`.

For one role at a time it:

1. takes the currently live role XUDP UUID from Iran
2. bootstraps the clean new foreign VPS
3. installs the live UUID on the new foreign XUDP endpoint and new client bundle before cutover
4. runs a foreign carrier -> loopback XUDP backend preflight
5. pulls the verified bundle to Iran
6. stops autoheal temporarily
7. changes only the selected Iran carrier
8. requires TCP + Telegram + actual UDP/XUDP role checks
9. rolls back the selected carrier on cutover failure
10. re-enables autoheal
11. refreshes dispatcher health for that role so new connections can use it again
12. cleans the old role configuration when the old VPS is still reachable non-interactively

Do not restart x-ui, the other carrier, the shared bridge, or the dispatcher as part of the carrier cutover itself.

## Trust replacement prerequisite

The existing Trust domain A record must point to the new Trust VPS before Trust installation/replacement because the new endpoint obtains a valid certificate for that hostname. The manager checks this and refuses to proceed if DNS has not moved.

## Fixed historical migration problems

v1.1 directly addresses these known issues:

- old UUID preservation helper could appear successful without producing the required live UUID invariant
- Trust role could pass direct HTTP while tunneled `xudp-trust.internal:2443` was unusable
- old carrier cutover validated path HTTP but not real role UDP/XUDP
- old autoheal treated TCP path HTTP as XUDP health
- old autoheal/dispatcher profile generated frequent deterministic background checks
- Telegram could be problematic even when generic HTTP health looked good

## Runtime authority

Real live server output is always more authoritative than this file. Endpoint IPs are intentionally not frozen here because role replacement is now a normal operator action.
